# Инвалидные места по умолчанию (#9) и детальные уведомления (#8)

Дата: 2026-08-21
Статус: согласовано, готово к плану реализации
Issues: [#9](https://github.com/Muxee4ka/TrainParserBot/issues/9), [#8](https://github.com/Muxee4ka/TrainParserBot/issues/8)

## Контекст и цель

Две открытые issue от @fdrov внешне независимы, но обе про одно: пользователь
видит в боте число и цену, которые не соответствуют тому, что он может купить.

- **#9** — места для инвалидов попадают в выдачу. Купить их в обычном сценарии
  нельзя, а стоят они часто заметно дешевле, поэтому именно они становятся
  «минимальной ценой» поезда.
- **#8** — уведомление сообщает только факт («найдено 1 место») и повторяет
  фильтр. Какой вагон, какое место, какая полка, почём — пользователь идёт
  выяснять на сайт РЖД, теряя время в гонке за билетом.

## Исследование API

Проведено на живом API 2026-08-21, маршрут Москва (2000000) → Ярославль
(2060000), дата 21.09.2026, выборка 8 поездов / 187 строк вагонов.

### Инвалидные места отдаются отдельной группой

Ключевой факт, определивший всю архитектуру:

```
поезд   помеченная CarGroup                   инвал. мест по CarPricing
063В    КУПЕ MinPrice=2452.2 Total=2          2
059А    КУПЕ MinPrice=3562.6 Total=8          8
038С    КУПЕ MinPrice=3941.1 Total=2          2
711М    СИД  MinPrice=1014.1 Total=4          4
713М    СИД  MinPrice=907.3  Total=4          4
715М    СИД  MinPrice=1344.2 Total=4          4
702М    КУПЕ MinPrice=2601.6 Total=2          2
703Х    КУПЕ MinPrice=2600.4 Total=2          2
```

В 8 поездах из 8 ровно одна `CarGroup` имеет `HasPlacesForDisabledPersons=true`,
и её `TotalPlaceQuantity` **точно равен** числу мест с
`Cars[].IsForDisabledPersons=true` в схеме вагонов. Смешанных групп (инвалидные
вперемешку с обычными) не встретилось.

**Следствие:** отбросить инвалидные места можно на уровне агрегатов
`train-pricing`, без единого обращения к дорогому `CarPricing`. Отбрасывается
группа целиком, обычные места при этом не теряются.

Масштаб проблемы на той же выборке: в 4 поездах из 6 проверенных минимальная
цена поезда была инвалидным местом, в трёх случаях — вдвое дешевле реально
доступной (1014 против 2093, 907 против 1814, 1344 против 2703).

### Значения `specialPlacesDemand` менять нельзя

Проверены все три значения перечисления в запросе `train-pricing`:

```
StandardPlacesAndForDisabledPersons  → поездов 20, мест 7319
StandardPlaces                       → поездов  0
ForDisabledPersons                   → поездов  0
```

РЖД отдаёт данные только при комбинированном значении. Серверная фильтрация
недоступна, отсюда клиентский предикат.

### Строка `Cars` — это не вагон

20 строк на 6 вагонов. Одна строка `Cars` = (вагон × тип полки × ценовая
корзина). Вагон 03 присутствует дважды как «Нижнее» с `MinPrice` 3752.6 и
4489.4. Отсюда для #8 доступны и номер места, и тип полки, и цена.

**Ограничение (принято):** в 14 строках из 187 (7.5%) `MinPrice != MaxPrice`,
например `063В ваг08 Верхнее: 2573.6..3015.7`. Цена внутри корзины не всегда
одна. Поэтому в уведомлении цена показывается как точная при `Min == Max` и как
`от N ₽` при разбросе — обещать точную цену за конкретное место нельзя.

## Объём

В объёме:
- Исключение инвалидных мест из всех агрегатных подсчётов и из минимальной цены
  по умолчанию, с возможностью отключить по подписке.
- Один сетевой вызов `CarPricing` на поезд вместо двух на пути уведомления.
- Детализация уведомления (вагон, место, полка, цена, класс) для всех фильтров,
  а не только для `cabin`/`pair`/`together`.

Вне объёма:
- Точная цена конкретного места (нет в API, см. ограничение выше).
- Изменение стоимости цикла опроса — она остаётся прежней (см. «Бюджет запросов»).
- Легаси `main.py` — отдельный артефакт, не трогаем.

## Часть 1 — #9: предикат в агрегатном слое

### Модель данных и миграции

Новая колонка `subscriptions.include_disabled INTEGER DEFAULT 0` по
существующему паттерну ad-hoc `ALTER TABLE ... ADD COLUMN` в
`database/manager.py`. Поле `Subscription.include_disabled: bool = False` в
`database/models.py`.

Дефолт `0` = инвалидные места скрыты, как просит issue. Существующие подписки
при миграции получают `0`, то есть меняют поведение — это намеренно и совпадает
с формулировкой «включить по умолчанию».

### Изменения в `services/rzd_api.py`

Сейчас `CarGroups` перебирается в трёх местах, и в каждом своя копия проверки
доступности: `count_seats_breakdown` (`:212`), `match_seats` (`:229`),
`min_price` (`:287`). Вводится один приватный предикат:

```python
@staticmethod
def _group_allowed(cg: Dict, include_disabled: bool = False) -> bool:
    """Учитывать ли группу вагонов. Инвалидные места РЖД отдаёт отдельной
    группой целиком (см. спеку 2026-08-21), поэтому достаточно отбросить
    группу по флагу — обычные места при этом не теряются."""
    if cg.get('AvailabilityIndication') != 'Available':
        return False
    if include_disabled:
        return True
    return not cg.get('HasPlacesForDisabledPersons')
```

Все три функции получают параметр `include_disabled: bool = False` и заменяют
свою проверку на вызов предиката. Публичный интерфейс не расширяется по смыслу:
вызывающему по-прежнему достаточно знать «дай подходящие места», а новый
параметр имеет дефолт, покрывающий 100% текущих вызовов.

### Вызывающие

`handlers/search.py` (6 вызовов `min_price`, 3 вызова `match_seats`) и
`services/monitoring.py` (3 + 2) продолжают работать без правок — дефолт
`include_disabled=False` даёт им новое желаемое поведение. Явно прокидывать
`subscription.include_disabled` нужно только там, где есть подписка:
`count_matched` (`services/monitoring.py:69`) и
`format_availability_message` (`:167`).

### UX

Кнопка-тумблер в панели фильтров (`services/filters.py`), callback
`flt_disabled_<0|1>`, по образцу существующих. В сводке фильтра строка
«Места для инвалидов: скрыты / показаны» — только когда включены, чтобы не
засорять типовой случай.

## Часть 2 — #8: шов вокруг схемы вагонов

### Проблема текущего интерфейса

`SeatMapService` (`services/rzd_seatmap.py:205`) — мелкий модуль: четыре
публичных метода (`detail_for_berth`, `count_for_berth`,
`empty_compartments_detail`, `empty_compartments`), каждый тонкая обёртка над
`_fetch` плюс чистая функция. Интерфейс почти равен реализации.

Прямое следствие — дефект производительности: на пути уведомления
`count_matched` (`services/monitoring.py:76`) делает `_fetch`, после чего
`format_availability_message` (`:192`) делает **второй `_fetch` того же поезда**
в том же цикле. Двойной сетевой вызов на каждый поезд в каждом уведомлении для
фильтров `cabin`/`pair`/`together`.

### Новый шов

Один сетевой метод, возвращающий значение; всё остальное чистое:

```python
class TrainSeats:
    """Разобранная схема вагонов одного поезда. Без сети."""
    def by_berth(self, berth, car_types=None, max_price=0, min_count=1) -> list
    def count(self, berth, ...) -> int
    def describe(self, berth, ..., limit=6) -> str   # вагон/место/полка/цена

class SeatMapService:
    def seats(self, route, train) -> Optional[TrainSeats]   # единственный сетевой метод
```

Глубина: интерфейс схлопывается с четырёх сетевых методов до одного, а вся логика
разбора и форматирования становится чистой и тестируемой без сети. Двойной
`_fetch` перестаёт быть возможным конструктивно — добыча явная и возвращает
данные, которые переиспользуются.

Существующие четыре метода сохраняются как тонкие обёртки над `seats()` ради
обратной совместимости тестов, но новые вызывающие идут через `seats()`.

### Формат уведомления

Для всех фильтров, не только seatmap-овских:

```
1. 🚂 063В Москва → Ярославль
   ⏰ 01:26 → 04:39 (3 ч 13 мин)
   ✅ Доступно (мест): 3

   🚃 Вагон 08 (купе)
   🛏 Место 015 (нижнее)
   💰 3752 ₽

   🚃 Вагон 11 (купе)
   🛏 Место 027 (нижнее)
   💰 от 2573 ₽
```

Цена без «от» при `MinPrice == MaxPrice` строки, с «от» при разбросе. Класс
вагона из `ServiceClassNameRu`, тип полки из существующего `_berth_kind`
(`services/rzd_seatmap.py:33`). Лимит — 6 мест на поезд, дальше «и ещё N»,
по образцу существующих `format_*` функций.

Инвалидные места в детализации отбрасываются по `Cars[].IsForDisabledPersons`,
если у подписки не включён `include_disabled` — то же правило, что в части 1, но
на точных данных.

## Бюджет запросов

| Путь | Сейчас | После |
|---|---|---|
| Цикл опроса, обычные фильтры | 1 запрос на подписку | без изменений |
| Цикл опроса, `cabin`/`pair`/`together` | +1 `CarPricing` на поезд | без изменений |
| Отправка уведомления, seatmap-фильтры | +1 `CarPricing` на поезд (второй) | переиспользуется первый |
| Отправка уведомления, обычные фильтры | 0 | +1 `CarPricing` на поезд (≤5) |

Цикл опроса не дорожает. Детализация добывается только на пути отправки
уведомления, который по построению редкий: `_filtered_state`
(`services/monitoring.py:95`) шлёт сообщение только когда счётчик изменился, и
поездов в сообщении максимум 5 (`:180`). Убранный двойной запрос примерно
компенсирует добавленный.

## Обратная совместимость

- Подписки без `include_disabled` читаются как `False` — поведение меняется
  намеренно, это суть #9.
- Четыре старых метода `SeatMapService` сохраняют сигнатуры.
- Формат `_filtered_state` (строка состояния) не меняется, поэтому существующие
  записи `subscription_states` не инвалидируются и не вызывают ложных
  уведомлений после деплоя.

## Тестирование

Юнит-тесты (без сети, на фикстурах):
- `_group_allowed`: доступная обычная / доступная инвалидная / недоступная, с
  `include_disabled` и без.
- `match_seats`, `count_seats_breakdown`, `min_price` на фикстуре с инвалидной
  группой: цена и счётчики не включают её при дефолте и включают при флаге.
- `TrainSeats.describe`: точная цена при `Min == Max`, «от N ₽» при разбросе.
- `TrainSeats` отбрасывает `IsForDisabledPersons` при дефолте.
- Миграция: чтение подписки, созданной до колонки.

Интеграционный (за `RUN_INTEGRATION_TESTS=1`): на живом ответе проверить, что
помеченная группа целиком инвалидная — инвариант, на котором стоит часть 1.
Если РЖД когда-нибудь начнёт смешивать, тест это поймает.
